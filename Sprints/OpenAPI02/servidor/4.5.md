4.5 · Reflexão crítica

31. Respostas às questões

1. Em T12, o token continuou a ser aceite após o termo de sessão no cliente. Que efeito teve, de facto, o termo de sessão? Que mecanismo seria necessário para invalidar o token no servidor, e com que implicações para o princípio do token autossuficiente?

O termo de sessão no cliente apenas eliminou a cópia do token que estava guardada na variável do módulo. Não invalidou o token no servidor, porque este não mantém um registo das sessões ativas. Para invalidar o token antes da sua expiração seria necessário implementar uma lista de revogação ou um mecanismo de sessões no servidor. Isso obrigaria o servidor a consultar informação adicional em cada pedido, reduzindo a autossuficiência do token.

2. Validade de 15 minutos: que vantagens e desvantagens resultariam de 15 segundos? E de 15 dias?

Uma validade de 15 segundos reduziria o período durante o qual um token roubado poderia ser utilizado, mas obrigaria o utilizador a autenticar-se frequentemente, prejudicando a utilização da aplicação. Uma validade de 15 dias seria mais cómoda, pois permitiria manter a sessão durante mais tempo, mas aumentaria o risco caso o token fosse roubado, uma vez que poderia ser utilizado durante um período muito maior. Os 15 minutos representam um compromisso entre segurança e comodidade.

3. O token é conservado numa variável do módulo e perde-se com o recarregamento da página. Comparar com localStorage quanto à exposição a ataques. Um cookie HttpOnly resolveria essa exposição? Que outro problema introduziria?

Uma variável do módulo mantém o token apenas enquanto a página está carregada, sendo eliminada quando esta é recarregada. O localStorage mantém o token mesmo depois de fechar ou recarregar a página, mas pode ser acedido por JavaScript, ficando exposto caso exista uma vulnerabilidade XSS. Um cookie HttpOnly impede o acesso ao token através de JavaScript, reduzindo esse risco. No entanto, introduz o risco de ataques CSRF, porque o browser envia automaticamente os cookies nos pedidos. Seriam necessárias medidas adicionais, como a proteção SameSite e mecanismos anti-CSRF.

4. O papel consta do token. Que alternativa existia, e quais as vantagens e desvantagens de cada opção quando o papel de um utilizador é alterado?

Uma alternativa seria guardar apenas a identificação do utilizador no token e consultar o papel atual na base de dados ou num ficheiro em cada pedido. Incluir o papel no token permite evitar essa consulta, tornando a verificação mais simples e rápida. No entanto, se o papel do utilizador for alterado, o token antigo continua a conter o papel anterior até expirar. Consultar o papel no servidor permite aplicar imediatamente as alterações, mas exige uma consulta adicional em cada pedido.

5. Com HS256, a verificação do token exige o conhecimento do segredo. Que problema surgiria se o cálculo das estatísticas fosse transferido para outro serviço, igualmente obrigado a verificar tokens?

O segundo serviço teria de conhecer o mesmo segredo utilizado para assinar os tokens. Isto significa que também teria capacidade para criar e assinar novos tokens, aumentando o risco caso esse serviço fosse comprometido. A partilha do segredo entre vários serviços dificulta a sua gestão e proteção.

6. Nada impede tentativas sucessivas de palavras-passe em POST /tokens. O contrato permite exprimir um limite? Onde teria de ser imposto, e com que código de resposta?

O contrato atual não define um limite de tentativas de autenticação. Esse limite teria de ser implementado no servidor ou numa camada de proteção, como um mecanismo de rate limiting, contando as tentativas realizadas num determinado período. Quando o limite fosse ultrapassado, poderia ser devolvido o código 429 Too Many Requests.

7. Em localhost, toda a comunicação ocorre em HTTP. Que proteção oferece um token Bearer numa rede sem HTTPS?

Um token Bearer não oferece proteção suficiente numa rede sem HTTPS, porque o token é enviado no cabeçalho Authorization sem encriptação. Alguém com capacidade para intercetar a comunicação poderia obter o token e utilizá-lo para se fazer passar pelo utilizador. O HTTPS é necessário para proteger a comunicação e impedir que o token seja facilmente intercetado.

8. Na API01, as regras de transição constavam apenas de texto; o mesmo sucede agora com as regras de autorização. Que garantias oferecem, respetivamente, o contrato, o servidor e os testes?

O contrato descreve as operações, os dados, os requisitos de autenticação e os códigos de resposta esperados, permitindo que os clientes saibam como utilizar a API. No entanto, não garante que as regras sejam realmente cumpridas.

O servidor implementa as regras de autenticação e autorização, verificando os tokens e os papéis dos utilizadores antes de permitir o acesso às operações.

Os testes permitem confirmar se o servidor se comporta como esperado em diferentes situações, incluindo pedidos sem token, tokens inválidos, utilizadores com diferentes papéis e tokens expirados. Assim, os três elementos complementam-se: o contrato especifica, o servidor aplica e os testes verificam.
